# 通用工具、任务模板与 LLM 挂载规则

> 2026-11-16 用户要求：工具与任务具备通用性，挂载规则充分说明，LLM 按规则挂载。设计约束已确认，本文为实现契约草案；后端适配能力须在实现时验证。配套产品范围见 `control-center.md`。

## 1. 当前差距与目标

当前 `src/core/backend.ts` 的 TurnRequest 只有 prompt / images / sessionId / abortSignal，没有任务绑定或工具挂载上下文。Claude 普通 profile 加载本机设置；Codex 经 CLI 启动。两者尚未实现按任务选择和约束工具的统一机制。

本设计增加独立的工具注册、任务模板、挂载解析与调用服务。LLM 依据说明选择适合任务的工具和模板，提交结构化挂载申请；服务端产生可执行的挂载结果。面板手工配置、CLI、定时任务和 LLM 共享同一套定义与校验。

## 2. 通用性：五类对象

| 对象 | 含义 | 复用方式 |
|---|---|---|
| ToolDefinition | 一种能力的契约、说明与实现引用 | 同一工具可供多个模板、任务和入口使用 |
| ToolBinding | 工具在本部署的实例：工作区、渠道、连接或凭据引用及允许范围 | 同一工具定义可以连接不同实例；凭据保留在服务端 |
| TaskTemplate | 可复用任务定义：输入、交付、执行方式、工具需求、挂载规则 | 手工创建、聊天派活和定时计划均可引用 |
| Task | 一次具体工作：目标、输入、业务状态、模板引用与任务级约束 | 跨聊天与面板使用稳定 ID 跟踪 |
| Run | 某任务的一次执行：执行器、输入及挂载快照、日志和结果 | 重试产生新 Run，历史可回查 |

Schedule 引用一个模板版本和显式输入，触发时创建 Task + Run。直接重跑已有任务产生新 Run。人工任务只依赖 Task；选择执行器时才创建 Run。

工具定义使用稳定、带命名空间的 ID，例如 `channel.send`、`report.render`、`script.execute`。业务名称保留在模板和部署绑定中。一个工具定义由内置服务、注册脚本或后续 MCP adapter 实现；首版覆盖内置服务与注册脚本，MCP adapter 另做适配验证。

注册脚本拥有自己的工具 ID、输入输出 schema 和说明；统一进程执行器只是实现适配层。脚本可同时被确定性任务直接调用和被 Agent 作为工具调用。

### 2.1 ToolDefinition 必填信息

| 字段 | 约定 |
|---|---|
| id / version / title / summary | 稳定标识、不可变版本、可搜索的摘要 |
| capabilities | 可实现的能力标签，供目录检索与模板匹配；标签只表达能力 |
| inputSchema / outputSchema | 输入输出 JSON Schema，服务端验证 |
| usage | 适用目标、前置条件、调用步骤、结果解释、可恢复错误的处理方式 |
| examples | 最少一个有效输入及输出形状；有副作用时说明结果 |
| effects | read / write / send / process 等效果及涉及的资源类型 |
| bindingSchema | 部署绑定配置的 schema，含凭据引用位置 |
| runtime | 所需执行环境、超时、并发键、取消能力、重试及幂等语义 |
| implementationRef | 由管理员登记的内置 handler 或注册脚本版本引用 |

规则字段与说明保持同一版本。目录摘要、工具详情、挂载指导及面板表单由同一注册记录派生。工具发布校验覆盖 schema、绑定要求、说明与示例的一致性。

### 2.2 TaskTemplate 必填信息

- id / version / title / summary / usage / examples。
- inputSchema 与输出、产物要求；完成条件与可自动检查的验收项。模型汇报与程序验收结果分别记录。
- executor：manual、tool 或 agent；tool 类型指定一个已注册工具和参数映射，agent 类型指定可选择的 profile 范围。
- toolRequirements：必要和可选能力、可选工具 ID 范围、所需绑定类型及默认绑定引用。
- mountPolicy：自动选择范围、每次运行工具数上限、资源范围、允许的效果和执行预算；使用明确字段表达。
- 使用说明指导 LLM 何时选此模板、需要收集什么输入、如何选工具和确定完成。

模板可以覆盖多种部署：例如同一“生成并发送日报”模板在不同工作区使用不同脚本和渠道绑定。输入与资源引用由实例配置补齐。

用户提出的新目标可以生成自定义 Task；其输入和执行需求仍经过同样校验。LLM 生成的可复用模板先作为草稿保存，验证发布后进入模板目录。

## 3. 挂载的准确含义

“挂载”是向某个 Run 授予一组确定的工具定义版本、部署绑定和资源范围，并提供对应的调用说明。它包含两个结果：模型获得可用能力的说明，服务端持有实际调用授权。

LLM 选择的是已登记的工具、绑定与资源引用。工具安装、注册脚本实现和配置凭据由控制中心的管理流程完成；LLM 可生成待配置草稿和说明，管理员发布后进入可挂载目录。

某个 profile 提供可用能力上限，某个模板声明任务需求。LLM 根据当前目标在这个范围内选择工具；最终资源范围取部署、profile、模板与任务约束的交集。调用实例使用该交集和实际参数再次校验。

### 3.1 可执行规则

| 规则 | 服务端行为 | 返回给 LLM 的信息 |
|---|---|---|
| 目录来源 | 从当前部署已发布且当前主体可发现的工具、模板及绑定中检索 | 目录版本、候选摘要与可用状态 |
| 完整说明 | 挂载申请引用已读取的工具详情版本及模板规则版本 | 输入输出 schema、usage、前置条件和效果 |
| 目标匹配 | 必要能力由选中工具的能力集合覆盖；LLM 给出工具用途与目标的对应理由 | 缺少的能力或输入；语义理由留作可见记录 |
| 范围匹配 | 所选工具、绑定、资源、效果满足各层允许范围 | 允许范围及具体冲突字段 |
| 前置条件 | 检查绑定配置、运行环境、连接及 adapter 能力 | ready / needs_configuration / unsupported 等状态 |
| 输入完整 | Task 与工具参数分别按 schema 校验，必填资源通过稳定引用绑定 | 缺失字段及其 schema 路径 |
| 精简挂载 | 检查数量和预算上限，展示每个工具的目的 | 实际挂载项和预算；目的合理性由用户/模型判断，程序按规则约束 |
| 一次执行的版本 | Run 固定模板、工具、绑定配置、policy 及实现版本摘要 | 挂载版本、变更历史和来源 |
| 执行时校验 | 每次调用校验 Run 身份、挂载、输入、当前启用状态与资源范围 | 结构化结果或明确错误码 |

挂载后，绑定中保存的是资源引用和配置版本；调用时凭据由宿主解析，并检查凭据及绑定当前是否可用。显式撤销、停用和策略收紧从后续调用起生效，历史快照保留用于追溯。已经发生的外部效果记录实际结果；运行中的进程按取消能力处理。

## 4. LLM 按规则挂载的完整流程

### 4.1 固定的管理协议

以下是 Home Agent Gate 的应用协议草案，具体 SDK/MCP 名称由 adapter 映射。

| 操作 | 输入要点 | 输出要点 |
|---|---|---|
| catalog.search | 目标、所需能力、类型 tool/template、分页游标 | 可发现的候选及版本、目录 revision |
| catalog.describe | 工具/模板 ID 与版本 | 完整 schema、usage、规则、前置条件、可见绑定摘要 |
| mounts.preview | taskId、预期挂载 revision、工具与绑定选择、资源引用、用途、规则版本 | 每项检查结果、规范化候选计划、previewId 与过期时间 |
| mounts.apply | previewId、预期 revision、幂等键 | 挂载快照 ID、新 revision、实际能力范围及说明 |
| tools.invoke | 挂载中的工具 ID、参数、调用幂等键（如适用） | 经 schema 校验的结果或错误 |

taskId 在挂载操作中必须属于当前可操作范围；执行调用的 runId 与身份由宿主绑定到会话和调用通道，工具参数只提供业务输入。固定管理协议遵守各自权限：Router 可发现目录并准备任务挂载，Worker 使用本任务的挂载，管理配置在授权的控制中心接口执行。

### 4.2 决策步骤

1. Router 根据用户目标查找模板；命中时读取模板详情并收集输入；自由任务则记录目标、交付与能力需求。
2. LLM 根据需求检索候选工具，读取所选版本的完整说明，选择具体部署绑定与资源范围，并为每项写清用途。
3. LLM 提交 preview。服务端返回可执行检查结果；字段缺失时补齐输入，连接未配置时呈现配置入口，范围冲突时在允许范围内调整计划。
4. preview 通过后，LLM 调用 apply。服务端再次校验当前 revision、有效期和前置条件，原子记录挂载结果及操作者。
5. Worker 获得任务说明、有效挂载说明和统一工具桥接入口，实际调用走 tools.invoke；调用记录进入该 Run。
6. 任务目标扩展时，Worker 经已有任务报告机制提出能力请求，Router 按新目标重新 preview / apply。新的挂载在调用边界生效；每次调用记录所用挂载 revision。
7. Run 结束后，挂载的可调用生命周期结束，历史快照与调用记录继续可查。

原有 Router 负责派活、Worker 负责执行的边界保留。Worker 的 report/question 属于引擎提供的基础运行能力，其作用域固定在当前任务；Router 的任务管理工具作用域固定在当前用户可管理的任务。

### 4.3 提供给 LLM 的规则文本

以下文本由服务端根据实际目录和规则生成，采用正向步骤：

> 根据任务目标与交付要求搜索任务模板和工具。读取选中条目的完整说明及版本，按前置条件收集输入。选择已配置的绑定及满足目标的资源范围，为每个工具说明用途。通过 mounts.preview 检查计划，根据返回字段补齐输入或调整选择；通过后调用 mounts.apply。使用返回的挂载清单及参数 schema 执行调用。新增能力需求通过任务报告提出，由 Router 更新挂载。根据实际工具结果和验收项汇报完成情况。

模板 usage 和工具 usage 补充领域方法，服务端返回的有效约束补充当前部署范围。工具结果和外部内容作为任务数据处理；目录定义与 policy 由受控管理流程维护。

## 5. 后端适配与调用边界

初版优先提供固定的工具桥接入口，LLM 在目录中发现并挂载业务工具后，经桥接调用同一 ToolService。这样业务目录与挂载无需依赖某个 harness 的动态 schema 更新能力。完整 schema 与版本由 describe 和挂载结果提供，实际输入始终由服务端验证。

adapter 在运行前声明并验证：工具桥接、会话隔离、内置工具限制、外部配置隔离、取消、续会话和结果传递等能力。Agent 类型执行模板只有在所需能力满足时才可调度。

- Claude 普通 profile 当前加载本机设置，需要增加受管执行模式及桥接适配；具体 Agent SDK 配置通过官方文档和安装版本验证。
- Codex 当前 CLI wrapper 尚未提供任务工具桥接和细粒度挂载约束，需要独立适配验证。配置界面显示实际支持情况。
- 受管任务使用经检查的受限工具集合和受控运行环境；若某个后端具备更广的 shell、文件或 MCP 入口，控制中心明确显示其授权范围，按该模式真实能力执行。
- 可强制的边界由宿主调用服务及执行环境共同提供；模型阅读了规则和工具被隐藏只代表上下文配置。受管挂载模式的启用条件包括执行约束验证。
- 续会话仅在任务、主体和约束一致时使用。权限收紧后重新检查 adapter 的续会话行为；需要隔离时新建会话并传递经过选择的任务摘要。

协议定义与后台模型无关。各 adapter 复用工具注册、Task/Run、policy 和调用日志，分别报告所能保障的执行范围。

## 6. 脱离 LLM 的使用方式

面板创建工具任务时选择模板或注册工具，按 schema 填参并选择绑定。挂载解析器以配置中的显式选择执行相同的 preview / apply。模板已经固定的挂载可以自动解析，结果仍会记录。

定时触发使用已保存的模板版本、输入与绑定选择，由代码解析并执行；模型只在 agent 类型的 Run 中使用。LLM 的一次性配置产物可以保存为经过验证的模板，之后由面板或定时器重复执行。

工具修改发布新版本，已有模板继续引用原版本；管理员升级模板时查看变更并校验。重试创建新 Run、重新解析并记录挂载，展示相较上次的变更。脚本版本使用实现摘要固定；变化后由注册更新流程产生新版本。

## 7. 示例：每日生成报告并发到聊天

同一任务模板声明输入 date、source、destination 和交付要求“报告文件 + 发送记录”。

- 工具：`report.build`（注册脚本，产出报告引用）、`channel.send`（内置服务，发送摘要或链接）。
- 绑定：report.build 绑定具体工作区与数据源；channel.send 绑定具体 bot 与目标聊天。
- LLM 配置：读取模板和工具说明，按用户意图选择 source / destination 对应绑定，preview / apply 后生成保存的任务模板实例。
- 日常运行：定时器传入日期，调用同一脚本和发送工具，保存产物、发送结果与失败原因。确定性模板的这条执行链由版本化实现定义；Agent 模板由模型选择调用顺序。
- 换部署：仍使用同一模板契约，配置本部署的脚本和渠道绑定。个人数据源、路径、收件人及凭据来自部署实例。

## 8. 控制中心必须展示的内容

工具库展示定义、usage、输入输出、实现方式、版本、绑定和可用状态；模板库展示用途、输入、交付、执行方式和所需能力。

任务详情展示：当前目标、模板来源、每个挂载工具及用途、可访问资源范围、选择者（用户 / Router / 定时配置）、检查结果、版本变更、调用日志和产物。用户可手工配置同样的挂载，LLM 选择过程以相同记录呈现。

## 9. 实现前验收清单

- 同一工具用于两个任务及两种入口，行为与校验一致；同一模板在两个部署绑定下可运行。
- LLM 按工具说明选择正确模板和绑定；输入不足时得到明确字段，配置不足时能定位配置入口。
- 模型选择符合说明与场景的质量用固定场景评估；程序规则约束用确定性测试验证，两者分别报告。
- preview/apply 覆盖并发修改、过期、重复提交、版本变化和能力缺失；幂等重试返回一致结果。
- 调用覆盖资源越界、绑定停用、凭据失效、参数错误和挂载结束；日志回溯到具体 Run 与 revision。
- adapter 验证工具桥接和实际执行范围；受管任务的每条可达执行通道满足声明的约束。
- 模型离线时，显式挂载、人工任务、脚本和定时执行保持可用。
- 挂载、模板、Task/Run 与调用结果通过 round-trip；真实模型选择与真实后端执行另记联调证据。

## 10. 实施依赖与优先级

P0：工具与模板 schema、目录及绑定管理、policy resolver、preview/apply、ToolService 与 Run 快照。它们与任务/配置基础一起实施。

P0：控制中心的工具库、模板库及挂载详情，先支持手工和确定性配置。

P1：受管后端桥接及执行范围验证、LLM 目录发现与挂载流程、Router / Worker 接入及场景评估。

注册脚本复用工具定义与调用服务；确定性定时任务复用模板与挂载解析器；通用可视化流程编排仍作为后续范围。
